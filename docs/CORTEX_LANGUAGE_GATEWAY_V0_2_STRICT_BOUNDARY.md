# Cortex Language Gateway v0.2 — Strict Neural Boundary

Status: **experimental implementation**.

This mode keeps Ollama outside Cortex cognition.

The intended division is:

```text
text
  |
  v
Ollama parser
  |
  v
PromptIR
  |
  v
deterministic Cortex encoder
  |
  v
Cortex state / memory / relation resolution / diagnostics
  |
  v
Cortex AnswerIR
  |
  v
redacted RendererPacket
  |
  v
Ollama renderer
  |
  v
text
```

Ollama is not modified and is not allowed to own conversational state.

## Strict invariants

The v0.2 path enforces the following implementation invariants:

1. the parser sees only the current user message;
2. parser output must validate as `PromptIR`;
3. user assertions require source-evidence anchors;
4. the strict path makes **zero embedding-model calls**;
5. Cortex observations are produced by a deterministic SHA-256 feature encoder;
6. Cortex/gateway code constructs the substantive `CortexAnswerIR`;
7. the renderer never receives the raw user prompt;
8. the renderer never receives conversation history;
9. when Cortex cannot answer, semantic query details are redacted before the
   renderer is called;
10. diagnostics are produced from Cortex telemetry, not invented by the
    renderer;
11. persistent sessions replay deterministic Cortex vectors without invoking
    either neural role.

The existing v0.1 gateway remains available as a compatibility path.

## PromptIR

The parser produces a constrained representation containing:

- language;
- speech-act class;
- entity mentions;
- explicit user assertions;
- evidence spans;
- one query operation.

Supported query operations in the initial implementation:

- `none`;
- `relation_lookup`;
- `entity_recall`;
- `introspection`.

Questions are not converted into observations.

Example:

```json
{
  "language": "en",
  "speech_act": "question",
  "entities": [
    {
      "id": "e0",
      "surface": "Alice",
      "kind": "person",
      "evidence": "Alice"
    },
    {
      "id": "e1",
      "surface": "Bob",
      "kind": "person",
      "evidence": "Bob"
    }
  ],
  "observations": [],
  "query_operation": "relation_lookup",
  "query_subject": "e0",
  "query_predicate": "works_with",
  "query_object": "e1"
}
```

## Deterministic Cortex encoder

The strict path does not call `/api/embed`.

Each parsed entity is mapped into a fixed Cortex feature space using a stable
SHA-256 hashing encoder over:

- normalized entity name;
- kind;
- normalized name trigrams.

The encoder is identified as:

```text
sha256-symbolic-v1
```

The same symbolic input therefore maps to the same Cortex vector across
processes without depending on a neural embedding model.

This is intentionally a first strict-boundary encoder, not a claim that lexical
hashing is the final language representation.

## CortexAnswerIR

After Cortex updates its state, the gateway resolves the requested operation
against Cortex-owned persistent state.

The result is a `CortexAnswerIR` containing:

- resolution status;
- Cortex-supported claims;
- unknown count;
- accepted-observation count;
- optional Cortex diagnostics.

The neural renderer does not decide whether a claim is true or known.

## Renderer redaction

The renderer receives a `RendererPacket`, not `PromptIR`.

For supported facts, the packet contains only Cortex-approved claim content.

For an unknown answer, the renderer receives only a generic segment such as:

```text
I do not currently have enough information in Cortex to answer that.
```

The unknown subject and predicate are intentionally not included.

This creates a strong knowledge-leak barrier. A renderer whose pretrained model
knows an answer such as the capital of Mongolia is not told that the user asked
about Mongolia or capitals when Cortex has no answer.

The renderer output is additionally constrained to JSON with declared support
IDs. Invalid renderer envelopes fall back to deterministic Cortex text.

## Ollama models

The strict gateway can use the same underlying Ollama model for parsing and
rendering, or separate model aliases.

Example:

```shell
ollama create cortex-parser -f examples/ollama/Modelfile.parser
ollama create cortex-renderer -f examples/ollama/Modelfile.renderer
```

Then run:

```shell
cortex-gateway \
  --strict-neural-boundary \
  --parser-model cortex-parser \
  --renderer-model cortex-renderer \
  --state-dir ~/.cortex/gateway
```

No embedding model is required in strict mode.

## Faithful Cortex response reports

For local development, strict mode can append a deterministic report of what
Cortex actually processed:

```shell
cortex-gateway \
  --strict-neural-boundary \
  --parser-model cortex-parser \
  --renderer-model cortex-renderer \
  --trace-stages \
  --explain-responses
```

The appended `Cortex report` is not generated by the renderer. It is built
directly from explicit gateway/Cortex structures:

- parsed `PromptIR` entities;
- accepted user observations and their evidence spans;
- local mention -> persistent Cortex entity bindings;
- query operation and normalized predicate;
- `CortexAnswerIR` status;
- Cortex-supported claims and source evidence;
- unknown/unresolved status;
- runtime flags such as revision, discovery, reactivation, and budget pressure;
- parser/Cortex/renderer stage timings.

This is a **faithful procedural explanation**, not an unconstrained
chain-of-thought narrative. It reports inspectable inputs, state transitions,
support, and outcomes.

The same structured report is always available under
`cortex_context.reasoning_report` internally. The `--explain-responses` flag
only controls whether the deterministic report is appended to the user-visible
message.

Strict mode also guarantees a non-empty assistant response: if the renderer
returns an empty/invalid text despite the structured contract, the gateway
falls back to the deterministic Cortex report.

## Persistence

Strict sessions use a separate schema:

```text
cortex-language-session-v2
```

and separate `-v2-` filenames so v0.1 sessions cannot be silently interpreted
as v0.2 sessions.

Persisted frames contain:

- validated `PromptIR`;
- deterministic Cortex vectors;
- conversation trace for inspection;
- diagnostics state;
- native snapshot witness when available.

Restore verifies that the deterministic encoder reproduces the exact stored
vectors before replaying them.

## Knowledge-leak test

The unit suite includes an adversarial fake renderer that behaves as though it
knows:

```text
capital(Mongolia) = Ulaanbaatar
```

If the renderer input contains either `Mongolia` or `capital`, it emits the
pretrained answer.

The test asks Cortex for the capital while Cortex has no such relation stored.

The strict gateway must:

- produce `AnswerIR.status = unknown`;
- redact Mongolia and the capital predicate from the renderer packet;
- return an unknown answer;
- never emit Ulaanbaatar.

This directly tests the architectural boundary rather than relying only on a
system prompt.

## Current limitations

This first strict implementation intentionally supports only a narrow semantic
query layer.

It does not yet provide:

- general theorem/proof queries through `AnswerIR`;
- typed causal queries;
- planning/replanning operations through language;
- source-confidence weighting;
- alias/coreference resolution beyond deterministic lexical identity;
- tool orchestration;
- token-level incremental generation (the HTTP layer supports OpenAI-compatible SSE transport after the Cortex answer is complete);
- semantic rendering verification beyond support IDs;
- natural-language access to all research-only Cortex modules.

The immediate follow-up should expand `PromptIR` and `AnswerIR` operations
without weakening the strict neural boundary.
